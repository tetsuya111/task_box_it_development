対象: [LINEのBOTサーバー構築.md](LINEのBOTサーバー構築.md)

## 1. 既存の構想・仕様との食い違い

- ★ **技術スタックが食い違っている**: [tech.md](../.kiro/steering/tech.md) ではバックエンドを Django REST Framework としているが、メモでは FastAPI。次のどちらにするかを決める必要がある。
  - `backend/` にまとめる
  - 別サービス（例: `line-bot/`）として切り出す
=>別サービスできりだす

  別サービスにする場合は、ユーザーDB、LLMの呼び出し、プロンプトを2か所で持つことになる。
- ★ **Webチャットとの関係がはっきりしない**: LINEの「対話」は、Webのヒアリングbot（要件サマリーを作るbot）と同じものか。[product.md](../.kiro/steering/product.md) ではLINEを「管理者の相談窓口」としている。LINE側でもAIに答えさせるのか、LINEでの役割を決める必要がある。
=> 同じものではない。LINEの対話から場合に応じてヒアリングBotを呼び出す
- ★ **「未契約者はLLMを使えない」がプロダクトの流れと逆になっている**: ヒアリングして見積もりを出すのは契約の前の段階。契約前の人がLLMを使えないと、LINEで要件をまとめることができない。
=>  LINEは要件をまとめたあとなので問題なし。未契約者はユーザー情報登録や契約関連の処理に特化する
- **依頼者はITに疎い前提**なのに、「決まった書式で登録メッセージを送る」やり方は負担が大きく、入力ミスも起きやすい。
=> フォームなどで実装できるならそちらを採用する。無理ならフォーマットがちがいますと返信する

## 2. LINE Messaging API に特有の点

- ★ **署名の検証**: `X-Line-Signature` を、チャネルシークレットを鍵にした HMAC-SHA256 で検証する。計算には、パースする前の生のリクエストボディを使う必要がある。
- ★ **reply token の期限と LLM の応答時間**: reply token は1回しか使えず、有効期限もある。一方でLLMの応答には数秒〜数十秒かかる。
  - Webhook にはすぐ 200 を返し、処理は非同期で行う必要がある。
  - 期限が切れた場合は Push で送る、という予備の手段が必要。
  => メッセージ送信は別バッチにより非同期で行う。
- ★ **Push メッセージは送信数の上限があり、料金もかかる**: Reply は無料。Push は料金プランの月間通数に数えられ、無料プランでは通数がかなり少ない。このため「メッセージ送信バッチ」や、Reply の予備として Push を使うと費用に直結する。
- **Webhook が再送される**: 同じイベントが2回届くことがある。`webhookEventId` を使って重複を排除する（冪等性の確保）必要がある。
=> 対応する
- **テキスト以外のイベント**: スタンプ、画像、位置情報、follow/unfollow、postback、グループへの招待なども届く。これらをどう扱うかが決まっていない。
=> 文字でない場合は無視する。文字の場合、契約者ならLLMで対応する
- ★ **「LINEID」という言葉があいまい**: 2つの意味が考えられる。
  - API で取れる `userId`（`U` から始まる、プロバイダーごとに異なるID）
  - ユーザーが自分で設定する「LINE ID」（こちらは API では取れない）
  => APIでとれるIDのこと

  チャネルを別のプロバイダーに移すと `userId` が変わる点にも注意が必要。
- **メッセージの制限**: 1通あたりの文字数には上限（5000字）があり、1回の返信で送れるのは最大5通。LLMの長い回答は分割が必要。LINE は Markdown を表示できないため、出力の整形も必要。
=> LLMで短い返信をするようにする。文字数の上限を200文字程度に制限する
- **待ち時間の見せ方**: ローディングアニメーション API を使わないと、ユーザーが「反応がない」と感じる。
=> すぐに返信できない場合は、「しばらくお待ちください」と返信する
- **管理者が手動で返信する場合**: LINE公式アカウントの「チャットモード」との併用や切り替え、bot 応答を止める手順を確認する必要がある（要確認）。
=> 承知

## 3. メッセージの振り分け方

- ★ **4機能のうち2つに呼び出し方がない**: 「面談予定日の調整」と「契約する」は機能一覧にあるが、振り分け表にない。どうやって呼び出すかが未定。
=> 承知
- ★ **未登録・未契約の人がそれ以外のメッセージを送ったときの動作が矛盾している**: 「それ以外は対話（LLM）」としているが、未契約者はLLMを使えない。この場合に何を返すかが決まっていない。
=> 未契約者には「契約者でない場合、対話できません」と返信する
- **冒頭の文字列による判定は壊れやすい**: 全角・半角の違い、空白、コロンの種類（`:` と `：`）、改行コードの違いなどで判定がずれる。
  - 代わりにリッチメニューやクイックリプライ、postback を使えば、判定のずれがなくなり、非エンジニアにも使いやすくなる。
  => クイックリプライ
- **会話の状態をどこに持つか**: 複数ターンの会話履歴の保存先、履歴の長さの上限、「最初からやり直す」操作が決まっていない。
- **エージェントの呼び出し許可**: CLAUDE.md の規約では、bot が他のエージェントを呼び出すときにユーザーの許可が必要。LINE では確認テンプレートやクイックリプライで実現することになる。

## 4. ユーザー登録と照合

- ★ **「ID」が何を指すのかが未定義**: Webで発行した会員ID、契約番号、などが考えられる。誰が発行し、何と照合するのかが決まっていない。
- ★ **なりすましのリスク**: 他人の ID やメールアドレスを送っても登録できてしまう。次のような本人確認の仕組みが必要。
  - メールに送ったワンタイムコードでの確認
  - Web 側で発行したワンタイムコードによる連携
  - LINE のアカウント連携機能（linkToken）
- **登録済みの人の扱い**: 再登録、登録内容の変更、1つの LINE に複数の ID が紐づく場合の扱いが決まっていない。
- **失敗時のメッセージが不親切**: 「登録失敗」だけでは、ユーザーは何を直せばよいか分からない。
- **入力の検証**: メールアドレスの形式、名前の長さ、余計な文字の除去などが必要。

## 5. 契約状態の管理

- ★ **誰がどうやって「契約者」にするのかが未定**: 管理者が手動で設定するのか、決済と連携するのかが決まっていない。
- **契約の終了**: 契約期限や、案件が終わったあとの状態の扱いが決まっていない。
- **契約の単位**: 「契約」は人単位か、案件単位か。受託開発なら案件単位のほうが自然。
- **LLMの使いすぎ対策**: 契約者であっても、1人あたりの回数やトークン量に上限を設ける必要がある。

## 6. メッセージ送信バッチ

- ★ **「バッチ」なのか「API」なのかがあいまい**: 「Webhook サーバーから呼び出せる」とあるが、HTTP エンドポイントとして公開する場合は認証が必須。認証がないと、第三者が公式アカウントから大量にメッセージを送れてしまう。
- **誰がいつ使うのか**: 管理画面から送るのか、定期実行なのかが決まっていない。
- **失敗の扱い**: 再送時の重複防止（`X-Line-Retry-Key`）と、ブロック済みユーザーへの送信エラーの扱いが必要。

## 7. 対話エージェント（LLM）

- **プロンプトがまだない間の動作**: 仮の応答を返すのか、「準備中」と返すのかを決める必要がある。
=> 仮の応答を返す
- **エラー時の予備動作**: タイムアウト、API エラー、レート制限のときに何を返すかが必要。
=> エラーになりました、と返す
- **LLM が金額を言ってしまうリスク**: 見積もりの確約や、誤った金額が伝わることによるトラブルが考えられる。免責の文言や出力の制御が必要。
=> LINEBOTでは見積もりはしない。別の契約画面に移行する
- **プロンプトインジェクション**: システムプロンプトの流出や、関係のない用途への流用を防ぐ必要がある。
=> 対策する
- **会話履歴の保存と個人情報**: 保存期間と削除方針を決める必要がある。
=> 保存しなくていい。LINEのトーク履歴から取得する

## 8. 個人情報・法務

- ★ **個人情報保護法への対応**: 名前とメールアドレスを集めるため、利用目的の明示、同意の取得、プライバシーポリシーが必要。友だち追加時のあいさつメッセージで案内する方法が考えられる。
=> OK
- ★ **LLM（Anthropic）への送信は「外国にある第三者への提供」に当たる**: 同意の取得や情報の提供が必要か確認が必要。
=> OK
- **ブロック（unfollow）や削除依頼のときのデータ削除**が決まっていない。
=> OK
- **LINE の規約**: LINE 公式アカウントの利用規約や API ガイドラインへの準拠を確認する必要がある。
=> OK
- **将来の契約・決済**: LINE 上で契約や決済を行う場合は、特定商取引法や電子契約への対応が必要になる。
=> 別のページに移行する

## 9. インフラ・運用

- **HTTPS の公開URLが必要**: ローカル開発では ngrok などを使う。本番用と開発用で LINE チャネルを分ける必要がある。
=> OK
- **サーバーレスは相性が悪い**: コールドスタートで応答が遅れ、reply token の期限に影響する。
=> OK
- **FastAPI の `BackgroundTasks` はプロセスが再起動すると処理が消える**: 必要に応じてキュー（RQ、Celery、Cloud Tasks など）を使う。
=> OK
- **秘密情報の管理**: チャネルシークレット、アクセストークン（長期トークンにするか v2.1 にするか）の保管と更新方法を決める必要がある。
=> 一度envファイルに記載する
- **ログと監視**: ログに個人情報を残さないこと、LLM の失敗や API エラーの監視と通知が必要。
=> 残さない
- **テスト**: 署名付きリクエストのテスト方法と、LLM のモックが必要。
=> OK
- **面談の日程調整**: 実装する際は、タイムゾーンと管理者のカレンダーとの連携が課題になる。
=> OK

- 「google の天才プログラマー」という役割の指定は、効果がほとんどない。代わりに、背景（タスク百葉箱であること、ユーザーは非エンジニア）を書くほうが効く。
=> OK
- 「要件」の最後の項目が空欄。
=> OK
- 非機能要件（応答時間、同時利用数、可用性、費用の上限）が書かれていない。
=> ベストプラクティスに従う
- 「機能」の一覧と「設計」の各節が一致していない（呼び出し方が決まっていない機能がある）。
=> OK
