# LINEのBOTサーバー構築（修正版）

元メモ: [LINEのBOTサーバー構築.md](LINEのBOTサーバー構築.md)
懸念点と回答: [LINEのBOTサーバー構築_懸念点.md](LINEのBOTサーバー構築_懸念点.md)

# 背景
- 「タスク百葉箱」は、小規模ツール開発を気軽に依頼できる受付プラットフォームである（[product.md](../.kiro/steering/product.md)）。
- 依頼者はWebのヒアリングbotで要件サマリーをまとめたあと、LINE公式アカウントで管理者（開発者本人）とやり取りする。LINE BOTはその窓口となる。
- 依頼者はITに疎い非エンジニアを想定する。依頼者向けの文言は専門用語を避け、短くする。

# 目的
LINE Messaging API の Webhook を受けるBOTサーバーを開発する。ユーザーの操作に応じて処理を分岐し、返信する。

# 要件
- LINE の Webhook を受けるAPIサーバーを構築すること
- ユーザーの操作に応じて処理を分岐すること
- Webhook の送信元ユーザーを、DBに登録されたユーザー情報と照合すること
- 未契約者はユーザー情報の登録と契約関連の処理のみ使える。LLMとの対話は契約者のみ使える
- LINE BOTでは見積もりをしない。見積もりや契約・決済は別のページで行う

# 設計

## 全体
- Python / FastAPI で構築する。Django REST Framework の `backend/` とは別のサービスとして切り出す
- ユーザーの識別には、Messaging API で取得できる `userId`（`U` から始まるID）を使う
- 未契約者と契約者で処理を分岐する
    - 契約状態の登録・更新は別の実装で行う。BOTサーバーは `userId` をキーに契約状態を参照するだけとする
- Webhook は署名（`X-Line-Signature`）を検証してから、すぐに 200 を返す。実際の処理とメッセージ送信は非同期で行う
- `webhookEventId` で重複イベントを排除する（LINE の再送に対して冪等にする）
- 非同期処理はプロセスの再起動で消えないよう、ジョブキュー（RQ など）で実行する

## イベントの扱い
| イベント | 処理 |
|---|---|
| テキストメッセージ | 「メッセージの振り分け」に従う |
| postback（クイックリプライ） | 対応する機能を呼び出す |
| 上記以外（スタンプ・画像・位置情報、follow/unfollow、グループ招待など） | 無視する |

- 友だち追加時の案内（利用目的・プライバシーポリシー）は、BOTサーバーではなく LINE Official Account Manager の「あいさつメッセージ」で設定する
- ブロック（unfollow）されてもユーザー情報は削除しない

## メッセージの振り分け
- 機能の呼び出しにはクイックリプライ（postback）を使う。先頭の文字列を解析して機能を判定するやり方はやめる
- 機能の一覧
    | 機能 | 未契約者 | 契約者 |
    |---|---|---|
    | ユーザー情報の登録 | ○ | ○ |
    | 面談予定日の調整 | ○ | ○ |
    | 契約する | ○ | ○ |
    | 対話（上記以外のテキスト） | × | ○ |
- 未契約者が上記以外のテキストを送った場合は、以下のメッセージを返し、機能のクイックリプライを表示する
    - メッセージ: 契約者でない場合、対話できません

## ユーザー情報の登録
- LIFF（LINE内で開くWebフォーム）で入力させる
- LIFF で実装できない場合は、以下のフォーマットでメッセージを送らせる。フォーマットに合わないときは「フォーマットが違います」と返し、正しい例を示す
- 入力させるのは名前とメールアドレスのみ。ID（`userId`）はユーザーに入力させず、サーバー側で取得する
    - メッセージの場合: 署名を検証した Webhook イベントの `source.userId` を使う
    - LIFF の場合: LIFF から送られた ID トークンをサーバー側で LINE の検証エンドポイントに問い合わせて検証し、その結果の `userId` を使う（クライアントから送られた `userId` をそのまま信用しない）
- 入力値を検証する（メールアドレスの形式、名前の長さ、前後の空白の除去）
- ユーザー情報と `userId` をDBに登録する
- 1つの LINE アカウントにつきユーザー情報は1件とする。登録済みのユーザーが再登録した場合は上書きする
- 登録できたら、以下のメッセージを送る
    - メッセージ: 登録完了
- 失敗したら、理由がわかるメッセージを送る（例: メールアドレスの形式が正しくありません）
### フォーマット（LIFF が使えない場合）
```
【ユーザー情報の登録】
名前: <名前>
メールアドレス: <メールアドレス>
```

### なりすまし対策
- `userId` は署名を検証した Webhook（または検証済みの LIFF ID トークン）からのみ取得するため、他人の LINE アカウントを名乗ることはできない
- 各機能の呼び出し時は、送信元の `userId` とDBに登録されたユーザー情報の `userId` を照合し、本人のユーザー情報・契約状態のみを参照する
- メールアドレスが本人のものかは確認しない（確認メールは送らない）。他人のメールアドレスを登録される可能性は残る

## 面談予定日の調整
- 一旦以下のメッセージを返す
    - メッセージ: 機能改修中

## 契約する
- 契約用の別ページへのリンクを送る（ページが用意できるまでは「機能改修中」と返す）

## 対話
- 契約者のテキストメッセージを対話エージェントに渡し、出力を返信する
- 返信は200文字程度までの短文とし、Markdown は使わない（プレーンテキスト）
- 返信の流れ
    1. Webhook で受け取ったら、reply token を使って定型文「しばらくお待ちください」を返す（Reply メッセージ）
    2. LLM の処理をジョブキューに登録する
    3. LLM の回答は「メッセージ送信バッチ」から、チャネルアクセストークンを使って送る（Push メッセージ）
- LLM がエラー（タイムアウト、APIエラー、レート制限）になった場合は、以下のメッセージを返す
    - メッセージ: エラーになりました
- 要件の整理が必要と判断した場合は、ユーザーに確認したうえで（クイックリプライで許可を取る）、Webのヒアリングbotへのリンクを案内する
- 見積もりや金額の話題には答えず、別のページへ案内する

### 会話履歴
- 文脈を引き継ぐため、直近の会話だけを短期間DBに保存する
    - 保存する件数: ユーザーごとに直近10往復まで（古いものから削除）
    - 保存期間: 最後のやり取りから24時間。期限を過ぎた履歴は定期的に削除する
- 履歴にはメッセージ本文（個人情報を含みうる）が入るため、ログには出力しない

### 対話エージェント
- 対話プロンプトに基づく（まだ作成しない）。それまでは仮の応答を返す
- プロンプトインジェクション対策をする（システムプロンプトを出力しない、用途外の依頼は断る）

## メッセージ送信バッチ
- ユーザーの `userId` とメッセージを指定して、ユーザーにメッセージを送る
- APIサーバー（BOTサーバー）が非同期でメッセージを送りたいときに、ジョブキュー経由で実行する（例: 対話の LLM 回答の送信）
- 外部には公開しない（HTTP エンドポイントを作らない）。そのため呼び出し時の認証は不要とする
- reply token は使わず、チャネルアクセストークンを使って Push メッセージで送る
- Push メッセージは LINE 公式アカウントの月間メッセージ通数に数えられる。トークンを分けても通数はアカウント単位で数えられるため、対話1往復ごとに1通消費する前提で料金プランを選ぶ
- 送信の再試行では `X-Line-Retry-Key` を使い、二重送信を防ぐ
- ブロック済みユーザーへの送信エラーは記録するだけにし、再試行しない

# 非機能要件
一般的なベストプラクティスに従う。
- 応答: Webhook はすぐに 200 を返す（処理は非同期）
- 実行環境: 常時起動のサーバーを使う（サーバーレスはコールドスタートの遅延があるため避ける）。HTTPS の公開URLを用意する
- 環境: 本番用と開発用で LINE チャネルを分ける。ローカル開発では ngrok 等を使う
- 秘密情報: チャネルシークレット、アクセストークン、LLM の APIキーは `.env` に記載し、コミットしない（`.env.example` を用意する）
- ログ: 個人情報（名前、メールアドレス、メッセージ本文）はログに残さない。LLM や LINE API のエラーは記録する
- テスト: 署名付きリクエストのテストと、LLM のモックを用意する
- 費用: LLM の呼び出し回数に上限を設ける（1ユーザーあたり、1日あたり）

# 法務・運用
- 友だち追加時のあいさつメッセージで、利用目的とプライバシーポリシーを示し、同意を得る
- LLM（Anthropic）への送信は「外国にある第三者への提供」に当たりうるため、プライバシーポリシーに記載する
- ユーザー情報を削除する機能は実装しない。個人情報保護法に基づく削除依頼があった場合は、管理者がDBから手動で削除する
- 契約・決済は別のページで行う（特定商取引法などへの対応はそちらで行う）
- LINE 公式アカウントの利用規約・API ガイドラインに従う
- 管理者が手動で返信する場合の、チャットモードとの切り替え手順を確認しておく
